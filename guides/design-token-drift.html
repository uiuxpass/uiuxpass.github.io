How to catch design-token drift before it ships

8 min read · Updated 21 November 2026

Every design system drifts. A developer picks #2a5cf0 because it "looks like the brand blue". A button gets padding: 13px 18px because it fit the label. A browser default border sneaks onto a <button> nobody restyled. None of these break anything on their own. Together they are why a product starts to feel slightly off, and why every redesign has to start with an audit.

This guide shows a repeatable way to find drift with numbers instead of squinting at screens.

Why reading the CSS is not enough

The obvious approach is to search the stylesheet for hex codes and pixel values and compare them with your tokens. It misses three kinds of drift:

  • Browser defaults. Buttons, inputs and selects come with their own fonts, borders and padding. If nobody overrode them, they are not in your CSS at all.
  • Inheritance. A text colour set on a parent three levels up is invisible in the rule you are reading.
  • Computed values. 1.0625rem, calc() and percentages only become pixels in the browser.

The reliable source is the computed style of every visible element, measured in a real browser at the widths people use.

Step 1: get your tokens into one file

Any of these formats works: W3C design tokens JSON ($value, $type), Tokens Studio JSON, a flat {"color.brand": "#2457f5"} file, or a CSS file with custom properties. If your tokens live in Figma variables, export them first. If you have no tokens at all, your page's :root variables are a weak but honest starting point: the check then tells you whether the page is consistent with itself.

Step 2: measure five categories

For each visible element, at 1440 and 390 px wide, collect:

  1. Colours: text colour on elements that contain text, background colours that are not transparent, border colours where a border is drawn.
  2. Font sizes and font families on text.
  3. Spacing: margins, paddings and flex or grid gaps, ignoring zero and the left/right margins created by margin: auto centring.
  4. Corner radius.

Count each distinct value once per element, so one long list does not outweigh everything else.

Step 3: compare with tolerance, and say how far off

A colour within a distance of about 3 (out of 441 in RGB space) is the token, rendered. A colour at distance 9 is almost certainly drift: someone eyedropped the brand colour from a screenshot. A colour at distance 50 may be a missing token. Report the nearest token every time; it is usually the fix.

For sizes, allow half a pixel. Then set pass bars per category. These are the defaults we use and why:

CategoryBar (share of uses on-token)Why
Colours98%Colour drift is the most visible and the easiest to fix.
Font families100%An off-brand font is never intentional; usually a control that did not inherit.
Font sizes95%Rare one-offs (a badge, a legal line) can be acceptable.
Corner radius95%Mixed radii read as unfinished.
Spacing90%Optical adjustments are sometimes deliberate; the rest should be on the scale.

Step 4: read the results like a designer

Here is a real result from a small pricing page with one "rogue" button:

Design system check: 0/5 categories pass
  FAIL Colors: 72.7% of 11 uses on-token, 3 off-token values
       #2a5cf0 ×1 → nearest color.brand (#2457f5, distance 9); e.g. button.rogue
       #000000 ×1 → nearest color.ink (#111827, distance 49); e.g. button.rogue
       #6b7280 ×1 → nearest color.muted (#4b5563, distance 52); e.g. p.note
  FAIL Font families: 80.0% of 5 uses on-token, 1 off-token values
       arial ×1 → nearest inter; e.g. button.rogue

Three causes explain almost every finding:

  • Near-miss colours (distance under 15): replace with the token variable.
  • Browser defaults (#000000 borders and arial on buttons): add border: 0 and font-family: inherit to your button and input base styles. One rule fixes every instance.
  • Off-scale spacing in one component: fix the component's rule, not each element.

Values far from any token need a decision, not a fix: either the design system is missing something real, or the design should change. Put those in front of the design-system owner with a short pros and cons note.

Step 5: make it a habit

  • Run the check on every page you touch in a redesign, before and after.
  • Run it on new components before they go into the library.
  • Track the percentage per category over time; drift creeps back in releases with tight deadlines.

What a token check cannot see: hover, focus, error and empty states that are not visible on load, and images. List those as "not checked" rather than implying they pass.
