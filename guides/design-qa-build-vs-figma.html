Design QA: how to check the build matches the Figma file

7 min read · Updated 24 November 2026

Design QA is the step where a designer compares what was built with what was designed, before release. Done by eye, it takes an hour per screen and still misses things: a 2 px spacing change looks fine on its own and only shows up when you put the two side by side. Done with a fixed setup and a pixel comparison, it takes minutes and gives developers exact numbers.

1. Capture the build the same way the frame was drawn

Most "differences" in a design QA are setup errors. Match these before you compare anything:

  • Width. Set the browser viewport to the frame width, for example 1440 or 390 px. A page captured at 1366 px will never line up with a 1440 px frame.
  • Scale. If the Figma export is at 2x, capture the page at a device pixel ratio of 2. Compare pixels at the same scale, then report distances in design px (divide by 2).
  • Content. Use the same text, images and data as the frame. Real data that is longer or shorter moves everything below it.
  • Fonts. Wait until web fonts have loaded. A capture taken during the fallback font is not a real difference.
  • Motion. Turn off animations and carousels, or wait until they finish, so the capture is the final state.

2. Compare, then fix from the top down

Overlay the export on the capture (a slider or 50% opacity) and generate a difference map that marks every pixel that changed. Start with the highest difference on the page and work down.

Top down matters because differences cascade. Take a paragraph of 10 lines set at 16 px. If the design uses a 24 px line height and the build uses 22 px, the paragraph ends 20 px higher, and every element below it is now 20 px off. The difference map turns red from that point to the bottom of the page, but there is only one bug. Fix it, capture again, and most of the red disappears.

For scale: a 1440 × 900 capture has 1,296,000 pixels, so 1% of it is 12,960 pixels, about a 114 px square. Some difference always remains, because browsers and Figma draw text edges differently. Judge areas, not a single total.

3. What to check, in this order

OrderAreaWhat usually differs
1Layout and spacingContainer width, gaps between sections, padding inside cards. Often a value off the spacing scale, such as 18 px where the scale has 16 and 24.
2TypographyLine height, letter spacing, weight. Figma letter spacing in % maps to em in CSS: 2% is 0.02em. A line height of 150% is 1.5.
3ColourHex values close to a token but not equal, such as #111111 instead of #111214. Invisible to the eye, but a sign the value was typed by hand.
4Corners, borders, shadowsRadius 6 instead of 8, a 1 px border where the design has none, a heavier shadow.
5Icons and imagesWrong size, cropped differently, blurry at 2x.
6StatesHover, focus, pressed, disabled, error, empty and loading. These are often missing from the build because they were missing from the file.
7Other widthsRepeat at your phone width (often 390 px) and one width between breakpoints, where layouts tend to break.

4. Write tickets developers can act on

"The header looks off" starts a conversation. A ticket with numbers ends one. Include:

  • Where: page, width, element (with a cropped screenshot of design and build side by side).
  • Expected and actual: "Card padding 24 px in the design, 20 px in the build."
  • The token if there is one: "Use space-6 (24 px), not a typed value."
  • Severity: blocks use, visibly wrong, or polish.

Group tickets by cause. Ten spacing differences that all come from one wrong container padding are one ticket, not ten.

When the build is right and the design is wrong

Sometimes the developer made a better call: real content needed more room, or a state did not exist in the file. Update the design file so it stays the source of truth, and note the change in the ticket instead of asking for a revert.
